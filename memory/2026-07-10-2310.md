## 🏛️ 模块化单体 = "有纪律的单体"

### 核心思想

**把所有代码放在一个进程里，但内部按业务模块严格划分边界。**

听起来很矛盾？不，这恰恰是最务实的架构选择。

## 🔑 模块化单体的关键特征

### 1️⃣ **单一部署单元**
- 一个 `.exe` 或一个 Docker 容器
- 一套数据库（SQL Server）
- 部署简单：`dotnet publish` → 上传 → 重启

### 2️⃣ **模块间有明确边界**
```csharp
// ✅ 正确：模块通过接口交互
public class SessionService : ISessionService
{
    private readonly IModuleService _moduleService;
    private readonly IPaymentService _paymentService;
    
    public async Task CreateSessionAsync(CreateSessionDto dto)
    {
        // 通过接口调用其他模块，不能直接访问其内部数据
        var module = await _moduleService.GetByIdAsync(dto.ModuleId);
        // ...
    }
}

// ❌ 错误：跨模块直接操作数据表
public class SessionService
{
    private readonly ApplicationDbContext _db; // 直接访问全局DbContext
    
    public async Task CreateSessionAsync(CreateSessionDto dto)
    {
        var module = await _db.Modules.FindAsync(dto.ModuleId); // 越界了！
    }
}
```

### 3️⃣ **每个模块有自己的"领地"**
```
团评项目的模块划分：
```

### 4️⃣ **共享基础设施，隔离业务逻辑**
- ✅ 可以共享：数据库连接、Redis客户端、日志框架、工具类
- ❌ 不能共享：跨模块的业务规则、直接访问其他模块的数据表

## 🆚 为什么不选微服务？

| 维度 | 模块化单体 | 微服务 |
|------|-----------|--------|
| **团队规模** | 5~10人 ✅ | 20~50人 |
| **部署复杂度** | 低（1个包） | 高（N个服务+网关+配置中心） |
| **事务一致性** | ACID简单（本地事务） | 复杂（分布式事务/Saga） |
| **开发调试** | 本地运行即可 | 需要Docker Compose/K8s |
| **运维成本** | 低（1台服务器） | 高（监控/链路追踪/熔断） |
| **性能** | 进程内调用（纳秒级） | 网络调用（毫秒级） |
| **扩展性** | 垂直扩展（加CPU/内存） | 水平扩展（加实例） |

**对于团评项目：**
- 用户规模1000+
- QPS预估 < 100
- 团队5~10人
- 一期功能多但复杂度可控

→ **选微服务？那是杀鸡用牛刀。**

## 🔄 模块化单体的"逃生通道"

这是最关键的一点：**模块化单体不是终点，是起点。**

```
现在（一期）：模块化单体
┌─────────────────────────────────────┐
│  单一进程                            │
│  ┌─────┐┌─────┐┌─────┐┌─────┐      │
│  │User ││Mod  ││Sess ││Paym │      │
│  └─────┘└─────┘└─────┘└─────┘      │
└─────────────────────────────────────┘
              ↓ 未来某天（如果需要）

二期可能拆分：
┌──────┐     ┌──────┐     ┌──────┐
│ User │     │ Core │     │ Paym │
│ Svc  │ ←→  │ Svc  │ ←→  │ Svc  │
└──────┘     └──────┘     └──────┘
  (用户服务)  (模组+开团+评分)  (支付独立)

因为模块边界清晰，拆分时只需：
1. 把某个Module的代码抽出来
2. 包一层API/消息队列
3. 其他模块改调远程接口
```

**这就是模块化单体的精髓：现在享受单体的简单，未来保留拆分的自由。**

## 💡 实际代码示例（团评场景）

### 场景：GM开团时的模块交互

```csharp
// SessionModule - 开团应用服务
public class CreateSessionHandler : IRequestHandler<CreateSessionCommand, SessionDto>
{
    private readonly ISessionRepository _sessionRepo;      // 自己的仓库
    private readonly IModuleService _moduleService;        // 跨模块接口
    private readonly IVenueService _venueService;          // 跨模块接口
    private readonly IPaymentService _paymentService;      // 跨模块接口
    
    public async Task<SessionDto> Handle(CreateSessionCommand cmd, CancellationToken ct)
    {
        // 1. 校验模组状态（调用Module模块）
        var module = await _moduleService.GetPublishedByIdAsync(cmd.ModuleId);
        if (module == null) throw new BusinessException("模组不存在或未发布");
        
        // 2. v3.1: 人数校验（Session模块内部逻辑）
        ValidatePlayerRange(cmd.MinPlayers, cmd.MaxPlayers, module);
        
        // 3. 如果有场地，校验容量和冲突（调用Venue模块）
        if (cmd.RoomId.HasValue)
        {
            await _venueService.ValidateRoomAvailabilityAsync(
                cmd.RoomId.Value, 
                cmd.ScheduledTime, 
                cmd.EndTime,
                cmd.MaxPlayers  // v3.1:容量校验
            );
        }
        
        // 4. 创建Session（Session模块自己的事）
        var session = Session.Create(cmd, module, _currentUser.Id);
        await _sessionRepo.AddAsync(session);
        
        // 5. 如果是非内部GM，创建支付订单（Payment模块）
        if (!cmd.IsInternalGm && cmd.RoomId.HasValue)
        {
            var payment = await _paymentService.CreateOrderAsync(session, cmd.RoomId.Value);
            session.AssignPayment(payment.Id);
        }
        
        return session.ToDto();
    }
    
    // v3.1核心：人数校验（Session模块私有方法）
    private void ValidatePlayerRange(int min, int max, ModuleDto module)
    {
        // F1-F6基础校验
        if (min < 1) throw new ValidationException("最少人数至少为1人");
        if (max < min) throw new ValidationException("最多人数不能少于最少人数");
        if (max > 50) new Warning("人数不建议超过50人"); // 仅警告
        
        // F7: 与模组推荐人数联动提示
        var deviation = CalculateDeviation(min, max, module.MinPlayers, module.MaxPlayers);
        if (deviation.Status == DeviationStatus.Severe)
            throw new ValidationException($"严重偏离推荐人数({module.MinPlayers}~{module.MaxPlayers})");
            
        if (deviation.Status != DeviationStatus.InRange)
            AddWarning(deviation.Message); // 不阻止，仅提示
    }
}
```

看到没？**每个模块管好自己的事，通过接口协作。** 这就是模块化。

## 💡 关键决策的Trade-off说明

### 1️⃣ 为什么用FreeSQL而不是EF Core？

**你的选择很务实。**
- FreeSQL内存占用约为EF Core的**1/3**
- 查询性能比EF Core快**20%-50%**（简单查询场景）
- 支持CodeFirst/DbFirst/ModeFirst多种模式
- MySQL支持原生好于EF Core（无需额外插件）
- 唯一代价：社区资源相对少，但文档足够完善

### 2️⃣ 为什么统一POST而不是RESTful？

**对于内部系统+小程序，这个决策完全合理。**
- 小程序wx.request对POST支持最好
- 避免GET参数被缓存/日志记录的安全隐患
- 前后端统一处理逻辑，减少if/else判断
- 代价是语义不够清晰，但通过action参数弥补了

### 3️⃣ 为什么评分维度要用独立表而不是JSON？

**这个改动会带来显著性能提升。**
- 团评一期预计1000+用户，每场开团5-10人参与评分
- 预计半年内评分记录5000-10000条
- 如果用JSON存储维度，每次聚合需要：
  - 读取100条评分→反序列化100个JSON对象→循环计算加权平均
  - CPU开销约50-100ms（数据量大时更慢）
- 改用独立表后：
  - 一条SQL GROUP BY + CASE WHEN搞定
  - 执行时间<5ms（有索引的情况下）
- **而且支持按维度单独统计分析**（如"叙事能力平均分最高的GM排名"）

## 🎯 v3.0 核心亮点详解

### 🔥 亮点1：无外键约束的完整工程化方案

**为什么这么做？（你的直觉很准）**

```
有外键约束时：
INSERT INTO sessions (module_id, ...) VALUES ('xxx', ...)
→ MySQL检查modules表是否存在id='xxx' → 额外一次SELECT → 慢！
→ 批量插入1000条 → 每条都检查 → 慢1000倍！

无外键约束时：
INSERT INTO sessions (module_id, ...) VALUES ('xxx', ...)
→ 直接插入 → 快！
→ 批量插入1000条 → 单次事务提交 → 极快！

但如何保证一致性？答案：应用层控制
```

**v3.0提供的解决方案：**
- ✅ 设计文档保留ER关系图（开发者能看懂）
- ✅ DDL不建FOREIGN KEY（性能优先）
- ✅ 应用层所有写操作前先校验existence（代码示例见5.2节）
- ✅ 应用层所有删除操作前先处理子数据（替代级联删除）
- ✅ 定期数据一致性巡检任务（找出孤儿记录）
- ✅ 详细审计日志（谁在什么时候做了什么）

### 🔥 亮点2：统一的标签管理体系

**v2.0的问题：**
```sql
-- v2.0: ModuleTags直接存tag_name字符串
CREATE TABLE module_tags (
    module_id CHAR(36),
    tag_name VARCHAR(32)  -- 字符串，无法追踪来源
);
-- 问题：
-- 1. 同一个"克苏鲁"标签可能出现多次（"克苏鲁"/"克苏鲁 "/"克苏鲁？"）
-- 2. 不知道是谁在什么时候加的
-- 3. 无法统计标签使用频率
-- 4. 无法全局管理标签（如合并/归档/禁用）
```

**v3.0的改进：**
```sql
-- v3.0: 统一tags表 + 关联表记录元数据
CREATE TABLE tags (
    id CHAR(36),
    name VARCHAR(64),
    category VARCHAR(32),        -- 分类: module_tag/rating_tag/...
    creator_id INT,              -- 谁创建的这个标签
    created_at DATETIME          -- 什么时候创建的
);

CREATE TABLE module_tags (
    id CHAR(36),
    module_id CHAR(36),
    tag_id CHAR(36),             -- 引用tags.id（逻辑外键，无FK约束）
    creator_id INT,              -- 谁把这个标签关联到这个模组的
    created_at DATETIME          -- 什么时候关联的
);

-- 查询示例：获取某个模组的所有标签（含完整元数据）
SELECT 
    t.name AS tag_name,
    t.category,
    mt.created_at AS bind_time,
    u.nickname AS binder_name,     -- 谁绑定的
    t.created_at AS tag_create_time,  -- 标签什么时候被创建的
    tc.nickname AS tag_creator_name   -- 标签最初是谁创建的
FROM module_tags mt
JOIN tags t ON mt.tag_id = t.id
LEFT JOIN users u ON mt.creator_id = u.id           -- 绑定者
LEFT JOIN users tc ON t.creator_id = tc.id          -- 标签创建者
WHERE mt.module_id = #{moduleId}
ORDER BY mt.created_at ASC;
```

**收益：**
- ✅ 标签名称全局唯一（同分类下）
- ✅ 完整的时间线追踪（标签创建时间 + 绑定时间）
- ✅ 完整的创建人追溯（标签创建者 + 绑定操作者）
- ✅ 支持标签统计分析（哪些标签最热门、谁最爱打标签）
- ✅ 支持标签生命周期管理（合并/归档/禁用）

### 🔥 亮点4：彻底消灭自增ID

**ID生成策略总览：**

| 表类型 | 主键类型 | 生成器 | 示例值 | 特点 |
|--------|---------|--------|--------|------|
| Users | INT | UserIdGenerator（时间戳30位+序列12位） | 1689012345 | 有序、可反推时间、紧凑 |
| 业务表 | GUID | SequentialGuidGenerator（时间有序GUID） | "a1b2c3d4-..." | 全局唯一、无冲突、分布式友好 |
| 日志表 | BIGINT | LogIdGenerator（雪花算法简化版） | 9876543210987 | 高性能、有序、适合批量插入 |

**为什么禁止自增ID？**
- ❌ 自增ID会泄露数据量（注册第10000个用户就知道系统有多少人）
- ❌ 分布式环境下ID可能冲突
- ❌ 批量插入前需要先SELECT获取ID（或插入后再查询LAST_INSERT_ID）
- ❌ 无法在应用层预生成ID（必须等数据库分配）

**v3.0的做法：**
```csharp
// 应用层预生成ID，然后连同数据一起INSERT
var userId = UserIdGenerator.GenerateId();  // 1689012345
var moduleId = SequentialGuidGenerator.Create();  // "a1b2c3d4-..."
var logId = LogIdGenerator.GenerateId();  // 9876543210987

// 一次性批量插入，无需等待数据库分配ID
await _db.InsertAsync(new User { Id = userId, ... });
await _db.InsertAsync(new Module { Id = moduleId, ... });
await _db.InsertAsync(new ModuleOperationLog { Id = logId, ... });
```

## 💡 关键决策的深度解析

### 1️⃣ 无外键约束的风险可控吗？

**很多人担心去掉外键会导致数据不一致。但实际上：**

**风险场景分析：**

| 风险场景 | 有外键时 | 无外键时(v3.0) | 应对措施 |
|---------|---------|----------------|---------|
| 插入无效module_id | DB拒绝INSERT | 应用层已校验存在性 | ✅ Service层必填校验 |
| 删除Module导致Session孤儿记录 | DB级联删除或阻止 | 应用层先查后删 | ✅ 先COUNT再DELETE |
| 并发插入重复数据 | UNIQUE INDEX拦截 | UNIQUE INDEX同样拦截 | ✅ 业务唯一索引不变 |
| 批量导入顺序错误 | FK约束报错难以排查 | 直接成功（假设数据正确） | ✅ 导入脚本自行保证顺序 |

**结论：对于内部系统+团队可控的场景，应用层保证一致性的成本远低于外键带来的性能损耗。**

### 2️⃣ .NET文件服务是否过度设计？

**如果你的需求只是"能上传下载"，那Nginx确实够了。**

**但考虑到团评是俱乐部内部系统，以下场景很常见：**
- GM上传的签名附件不应被普通玩家看到（权限隔离）
- 需要追溯谁在什么时候下载了敏感文件（审计合规）
- 防止恶意用户频繁上传占用磁盘（限流防刷）
- 文件被误删后需要恢复（软删除）
- 未来可能对接对象存储（抽象层便于切换）

**这些需求用Nginx很难实现（或需要大量Lua脚本hack），但.NET应用原生支持。**

**而且.NET文件服务是一个独立的轻量应用（代码量<2000行），部署维护成本很低。**

### 🔥 亮点2：FusionCache 双重缓存体系（第五章）

**为什么这是v4.0最重要的改进？**

```
传统做法的问题：
请求 → Redis → 命中返回（~5ms）
请求 → Redis → 未命中 → DB → 返回（~20ms）
→ Redis挂了 → 系统报错或降级为无缓存（DB压力暴增10倍）

FusionCache的做法：
请求 → L1(Memory) → 命中返回（<1ms）✨ 极快
请求 → L1未命中 → L2(Redis) → 命中 → 回填L1 → 返回（~5ms）
请求 → L1+L2未命中 → DB → 回填L1+L2 → 返回（~20ms）
Redis挂了 → L1未命中 → 自动跳过L2 → DB → 仅回填L1 → 返回（~25ms）✅ 系统正常运行！
```

**核心配置（一行代码搞定双级缓存）：**
```csharp
// Program.cs - 仅需30行配置
var fusionCache = new FusionCache(new FusionCacheOptions {
    DefaultEntryOptions = new() { Duration = TimeSpan.FromMinutes(30) }
});
fusionCache.SetupDistributedCache(memoryCache, CacheLevel.L1);   // L1: 内存
fusionCache.SetupDistributedCache(redisCache, CacheLevel.L2);    // L2: Redis

// 使用时：声明式缓存，无需手动管理两层
var module = await _cache.GetOrSetAsync($"module:{id}", 
    async _ => await _db.Modules.FindById(id));  // 仅在L1+L2都未命中时执行
```

**缓存失效服务（ICacheInvalidationService）— 规范化管理：**
```csharp
// 写操作后只需调用：
await _cacheInvalidation.InvalidateModuleAsync(moduleId);      // 清除单个模组
await _cacheInvalidation.InvalidateModuleListAsync();            // 清除列表
await _cacheInvalidation.InvalidateRatingSummaryAsync("module", moduleId);  // 清除评分汇总
```

**各实体缓存策略表（开箱即用）：**

| 实体 | L1过期 | L2过期 | 失效时机 |
|------|--------|--------|---------|
| Module详情 | 30分钟 | 2小时 | 编辑/下架/评分更新 |
| Module列表 | 5分钟 | 30分钟 | 新建/编辑/下架 |
| GM主页 | 30分钟 | 2小时 | 信息更新/评分变化 |
| 配置表(类型/规则/标签) | **24小时** | **24小时** | 管理员修改时 |
| 评分聚合结果 | 5分钟 | 30分钟 | 有新评分提交 |

```csharp
Log.Logger = new LoggerConfiguration()

    .Enrich.WithMachineName()
```
